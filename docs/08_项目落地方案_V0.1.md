## 0. 执行结论

推荐采用：

> **网页验证核心叙事，Godot 尽早进入正式制作，微信小游戏按渠道价值单独决策。**

不建议把“网页 → 微信小程序 → Godot”设为所有项目必经路线。平台切换本身不会让作品更成熟，反而可能重复开发界面、存档、资源加载和适配。

最稳妥的路线是：

```text
阶段 A：文档与内容模式
→ 阶段 B：网页核心原型
→ 阶段 C：Godot 第一章垂直切片
→ 阶段 D：第一章公开试玩
→ 阶段 E：按章正式制作
→ 可选支线：微信小游戏演示 / 发行版
```

项目真正需要跨阶段复用的是：

- 故事节点和文本。
- 条件、效果与状态事件。
- 人物关系。
- 因果和档案版本。
- 记忆与跨章交接。
- 存档模式和版本升级规则。

## 1. 产品落地目标

### 1.1 核心用户体验

玩家每 5—12 分钟完成一个小循环：

```text
阅读场景
→ 检查人物、文书或地点
→ 获得不完整信息
→ 选择行动与承担者
→ 人物、资源、事实或记录发生变化
→ 立即获得有限反馈
```

每 30—60 分钟完成一个中循环：

```text
时代压力进入生活
→ 多名人物形成冲突
→ 职业权限打开一种解法
→ 玩家支付不可逆代价
→ 一个因果节点进入后续
```

每章完成一个大循环：

```text
苏醒
→ 入世
→ 分流
→ 种因
→ 承担本世结果
→ 形成档案
→ 交给后世
```

### 1.2 MVP 与正式目标

| 阶段 | 内容 | 建议时长 | 成功标准 |
|---|---|---|---|
| 技术样片 | 1 个场景、2 人物、1 次档案分歧 | 10—15 分钟 | 能保存、读取、回放选择 |
| 核心原型 | 序章—第一章 ACT02 | 30—45 分钟 | 玩家理解本世身份、关系、代价和记录分层 |
| 垂直切片 | 第一章完整一生 | 3—5 小时 | 美术、音频、职业、因果和跨章接口闭环 |
| 公开试玩 | 垂直切片优化版 | 1—2 小时可独立试玩 | 新玩家无需作者解释即可理解 |
| 正式章节 | 每章一个可发布内容包 | 2.5—4 小时首轮 | 内容生产和质量稳定 |
| 全游戏 | 七章加终章 | 20—30 小时首轮 | 跨章因果和身份长线完整回收 |

## 2. 技术路线决策

### 2.1 三种路线比较

| 路线 | 优点 | 代价 | 适用条件 | 结论 |
|---|---|---|---|---|
| 网页 → Godot | 原型快；正式版 2D 与跨平台能力更完整 | UI 和运行时需重做一次 | PC / 独立游戏为核心 | **默认推荐** |
| 网页 → Cocos / 微信小游戏并长期使用 | TypeScript 复用较多；微信与移动发行成熟 | PC 原生体验和团队引擎偏好需评估 | 微信 / 移动是第一市场 | **渠道优先时选择** |
| 网页 → Cocos / 微信 → Godot | 能依次试多个平台 | 两次运行时迁移、两套适配、维护成本最高 | 有独立平台团队和明确商业理由 | **不作为默认路线** |

### 2.2 为什么是微信小游戏，不是普通小程序

《山河无名》属于游戏交互，应评估微信小游戏。小游戏运行环境不是普通浏览器，需要适配平台 API、资源分包、远程资源、缓存和包体限制。

微信版本更适合：

- 15—30 分钟序章。
- 第一章的传播型试玩。
- 轻量章节发行。

它不适合作为“中期做完后一定丢弃”的过渡工程。

### 2.3 Godot 版本和语言

推荐：

```text
引擎：Godot 4.x 稳定分支
语言：GDScript
渲染：2D，Compatibility 路径优先验证
核心平台：Windows PC
扩展平台：Linux / macOS / Android，按实测决定
网页导出：作为试玩可能性验证，不承诺等同原生版
```

截至 2026-07-01，Godot 4.7 已发布不久。生产项目不应只因“最新”立即升级。建议：

1. 用当前经过补丁验证的稳定分支建立技术样片。
2. 用同一内容包测试 4.7 的字体、音频、存档、渲染和网页导出。
3. 在第一章美术量产前锁定版本。
4. 只在章节里程碑之间升级。

如果网页导出是正式要求，主工程不采用 C#。Godot 4 官方文档说明 C# 项目不能导出到 Web。

### 2.4 网页原型栈

推荐：

```text
构建：Vite
语言：TypeScript
界面：React 或 Preact
测试：Vitest + Playwright
数据校验：JSON Schema
存档：IndexedDB，开发期同时支持 JSON 导入 / 导出
```

原型目标不是做出最终网页美术，而是验证：

- 节点能否流转。
- 选择能否产生明确状态事件。
- 真相、官档、私录、口述是否可被玩家理解。
- 存档能否在内容更新后升级。
- 编剧是否能在不改程序的情况下增加内容。

## 3. 平台无关架构

### 3.1 推荐目录

```text
content/
  schema/
    chapter.schema.json
    scene.schema.json
    character.schema.json
    cause.schema.json
    save.schema.json
  chapters/
    ch01/
      chapter.yaml
      scenes/
      choices/
      callbacks/
  characters/
  causes/
  memories/
  records/
  assets/
    manifests/

packages/
  story-core/
    conditions/
    effects/
    state/
    save/
    validation/

apps/
  web/
  godot/
  wechat/

tools/
  content-compiler/
  route-auditor/
  save-migrator/
```

仓库当前可先采用更小结构，等序章—ACT02 跑通再拆成工作区。目录目标用于约束边界，不要求第一天一次建完。

### 3.2 内容节点建议

单个节点至少包含：

```yaml
id: CH01-ACT01-SC001
speaker: narrator
text: "……"
conditions: []
choices:
  - id: C01
    label: "先查看木牌"
    conditions: []
    effects:
      - type: fact.set
        key: ch01.saw_wooden_tag
        value: true
      - type: relationship.change
        character: NPC_ID
        field: trust
        amount: 1
    next: CH01-ACT01-SC002
```

正式模式还要支持：

```text
scene.enter
fact.set
resource.change
relationship.change
record.write
record.redact
testimony.learn
cause.activate
cause.resolve
memory.trigger
carrier.assign
chapter.handoff
```

### 3.3 状态分区

```text
world       历史与地方的共享状态
player      本世身份、资源、伤病与权限
relations   人物信任、共同债、裂痕与去向
facts       实际发生
knowledge   玩家已知
records     官档、私录和口述
causes      因果节点生命周期
memories    触发、误认与揭示层级
handoff     跨章交接包
meta        设置、章节解锁和存档版本
```

所有改变通过事件写入，不允许 UI 直接偷偷修改状态。这样才能：

- 回放错误。
- 自动测试路线。
- 生成本世档案。
- 升级旧存档。
- 把同一内容接到网页和 Godot。

### 3.4 存档原则

存档至少包含：

```text
save_version
content_version
current_node
state_snapshot
event_log
chapter_handoffs
playtime
created_at
updated_at
```

每次内容模式变化必须提供迁移函数。开发期保留 JSON 导入导出，便于编剧、测试和问题复现。

## 4. 内容生产流程

### 4.1 从文档到可玩内容

```text
历史研究卡
→ 章节命题与人生窗口
→ 人物关系网
→ 共享事件脊柱
→ 职业信息 / 权限 / 责任差异
→ 因果与档案节点
→ 场景对白
→ 结构化内容
→ 自动校验
→ 可玩评审
→ 历史与语言复核
```

### 4.2 每个场景的制作卡

每场至少回答：

1. 现实目标是什么？
2. 哪些人物分别想要什么？
3. 玩家当前知道什么，不知道什么？
4. 当前职业能做什么，不能做什么？
5. 选择的代价由谁承担？
6. 事实和记录是否产生分歧？
7. 哪个状态会进入后续？
8. 需要哪些背景、立绘、物件、声音和特效？

### 4.3 分支预算

推荐：

```text
70% 共享场景
20% 职业视角、方法和责任差异
10% 稀有回收、隐藏关系和结局差异
```

分支优先改变：

- 信息顺序。
- 可用方法。
- 谁信任玩家。
- 谁承担代价。
- 哪个版本被保存。
- 后续回收形态。

分支不优先复制整段历史主线。

## 5. 视觉落地

### 5.1 UI 结构

推荐四个常驻层级：

```text
场景层：背景、人物、轻视差与环境变化
叙事层：对白、旁白、选择与即时反馈
调查层：人物、物件、地图和文书
档案层：事实、官档、私录、口述和本世交接
```

“档案层”是本项目区别于普通 AVG 的关键界面。它不应把全部真相直接展示给玩家，而是明确标出：

- 这是玩家亲见。
- 这是某人证言。
- 这是官档写法。
- 这是民间版本。
- 这里存在矛盾或缺页。

### 5.2 资产优先级

第一章垂直切片的预算顺序：

1. 可读性和字体。
2. 核心人物立绘与表情。
3. 关键场景背景。
4. 木牌、简牍、钟、地图和无名录等可调查物件。
5. 章节首尾与长平等关键事件插画。
6. 局部动画、粒子和转场。
7. 低优先级装饰。

不要在原型阶段购买或制作大量无法复用的古风 UI。

### 5.3 色彩实施

基础色使用总框架的墨黑、暖纸、漆褐、青铜、朱砂、记忆靛和新生绿。工程中统一使用语义令牌：

```text
color.bg.primary
color.bg.panel
color.text.primary
color.text.secondary
color.action
color.danger
color.memory
color.renewal
color.chapter.accent
```

不要在节点内容中写死色值。章节只替换 `color.chapter.accent` 和少量场景调色。

## 6. 音频落地

音频分为：

- 章节主题。
- 裂钟变奏。
- 旧曲变奏。
- 地点环境。
- 劳动与制度声音。
- 关键选择反馈。

第一章原型只需要：

```text
1 首章节主题
1 个裂钟母题
4—6 个场景环境循环
8—12 个 UI / 物件声音
2—3 个关键事件短乐段
```

不建议在垂直切片前做全角色配音。优先使用关键句、气息和场景人声，等文本稳定、预算明确后再决定配音范围。

## 7. 阶段计划与闸门

排期以小型 3—5 人团队为参考；一人团队应按实际产能延长，不削减质量闸门。

### 阶段 A：内容模式与技术样片

建议周期：2—4 周。

交付：

- 节点、人物、因果、记录和存档模式。
- 最小故事运行器。
- 一个 10—15 分钟场景。
- JSON 存档导入导出。
- 基础路线校验。

通过条件：

- 编剧只改内容文件即可增加节点。
- 同一选择能同时改变人物、事实和记录。
- 存读档后状态一致。
- 错误节点能被自动发现。

### 阶段 B：序章—ACT02 网页核心原型

建议周期：4—8 周。

交付：

- 30—45 分钟可玩内容。
- 苏醒、入世、关键故人和第一次现实选择。
- 档案界面第一版。
- 基础声音和占位美术。
- 5—10 名外部测试者。

通过条件：

- 大多数测试者能说清自己做了什么、谁承担了代价。
- 大多数测试者能区分“事实”和“记录”。
- 无需作者在旁解释操作。
- 关键节点无死路，存档可恢复。

### 阶段 C：Godot 第一章垂直切片

建议周期：4—8 个月，取决于团队和资产量。

交付：

- 第一章一段完整人生。
- 共享主线与有限职业差异。
- 正式 UI、美术和音频基线。
- 本世档案与第一章至第二章交接。
- Windows 可执行版。

通过条件：

- 首轮 3—5 小时，无致命断路。
- 主要职业位置都能完成共享主线。
- 无名录四种去向都能生成合法交接包。
- 至少 20—50 名目标用户完成测试。
- 资产制作速度能够估算单章成本。

### 阶段 D：公开试玩与制作决策

建议周期：6—10 周。

交付：

- 1—2 小时公开试玩。
- 商店页或发行页素材。
- 崩溃、性能、字体和兼容性修复。
- 用户反馈报告。
- 第二章是否立项的预算与排期。

进入第二章的必要条件：

- 玩家对题材和核心机制有真实兴趣。
- 叙事完成率和关键选择分布可解释。
- 团队能稳定生产文本、美术和测试内容。
- 资金和人力能支持至少一个完整章节周期。

### 阶段 E：章节化正式制作

每章采用：

```text
预制作
→ 史实与人物评审
→ 共享主线灰盒
→ 职业差异
→ 美术音频量产
→ 全路线审计
→ 发布
→ 跨章存档验证
```

第 N+1 章可在第 N 章美术量产后开始历史预研，但不能在第 N 章结构未稳定前大量写正式对白。

## 8. 微信小游戏决策点

不在阶段 A、B 立即建立微信工程。阶段 B 完成后，根据以下问题打分：

| 问题 | 是 | 否 |
|---|---|---|
| 目标用户是否明显集中在微信传播链？ | +1 | 0 |
| 30 分钟内的体验是否能独立成立？ | +1 | 0 |
| 是否有专人维护渠道适配和审核？ | +1 | 0 |
| 美术与音频能否适应分包和远程资源？ | +1 | 0 |
| 微信版本是否有明确转化或收入目标？ | +1 | 0 |

建议：

- 0—2 分：不立项。
- 3 分：只做技术验证。
- 4—5 分：建立独立微信小游戏发行计划。

如果微信成为主平台，应认真评估 Cocos Creator 3.8 LTS 作为长期引擎；如果 PC 独立游戏仍是核心，则微信版本只做受控内容子集。

## 9. 测试与质量保障

### 9.1 自动校验

每次内容提交至少检查：

- ID 唯一。
- 所有 `next` 节点存在。
- 条件字段合法。
- 效果类型合法。
- 必到节点可达。
- 结局可达。
- 互斥状态不会同时出现。
- 因果节点存在回收或断链兜底。
- 所有跨章载体能生成合法交接包。
- 文本引用的角色和资产存在。

### 9.2 自动路线遍历

建立无界面模拟器，批量随机或策略遍历路线，输出：

```text
不可达节点
死循环
无出口节点
永远无法满足的条件
未回收因果
冲突记录
非法交接包
```

### 9.3 人工评审

自动测试不能替代：

- 历史审校。
- 人物动机评审。
- 语言时代感。
- 情绪节奏。
- 选项是否存在作者暗示的唯一正确答案。
- 普通人是否被写成工具和苦难景观。

## 10. 团队与职责

### 10.1 最小团队

| 职责 | 核心工作 |
|---|---|
| 主创 / 叙事设计 | 总纲、章节命题、人物、场景和最终取舍 |
| 历史研究 / 编辑 | 史实清单、争议说明、物质生活与语言校验 |
| 程序 / 技术设计 | 故事运行器、工具、存档、平台和测试 |
| 2D 美术 / UI | 视觉基线、角色、场景、文书和交互界面 |
| 音频合作 | 主题、母题、环境与关键反馈 |

制作人职责必须有人承担：控制范围、版本、预算、验收和发行。不能默认由“大家一起”完成。

### 10.2 资产台账

每章立项时统计：

```text
场景背景数量
人物立绘和表情数量
关键事件插画数量
可调查物件数量
章节音乐和环境声音数量
文本字数与节点数量
每条职业独有场景数量
```

超过垂直切片测得产能时，优先合并场景和分支，不通过加班维持错误范围。

## 11. 版本与发布

建议版本：

```text
content_version: 内容版本
runtime_version: 运行时版本
save_version: 存档模式版本
chapter_version: 单章版本
```

每章发布前：

1. 锁定内容模式。
2. 备份并测试上一版存档。
3. 输出变更说明。
4. 运行全部路线审计。
5. 用干净环境安装。
6. 验证字体、输入、音频、窗口和本地化占位。

章节制不能以破坏旧存档为代价。若历史修订必须改变旧节点，迁移后保留玩家原选择的语义，而不是悄悄重算。

## 12. 当前 90 天可执行清单

### 第 1—2 周

- 冻结 V0.4 总框架。
- 定义 `scene`、`character`、`cause`、`record` 和 `save` 模式。
- 从 ACT01 选择一个 10—15 分钟场景做技术样片。

### 第 3—6 周

- 完成最小故事运行器。
- 完成存读档和事件日志。
- 完成事实 / 官档 / 私录 / 口述的第一版界面。
- 加入自动节点校验。

### 第 7—10 周

- 结构化序章—ACT02。
- 完成基础关系、资源、记忆和档案反馈。
- 使用占位美术完成 30—45 分钟网页原型。

### 第 11—12 周

- 进行第一轮外部测试。
- 汇总理解偏差、无效选择和节奏问题。
- 决定 Godot 垂直切片范围。
- 仅在数据证明渠道价值时启动微信小游戏技术验证。
